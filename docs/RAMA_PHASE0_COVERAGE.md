# RAMA Phase 0 — Capability Coverage Audit

> Companion to `RAMA_SMARTNESS_ARCHITECTURE.md`. This is the **evidence**: a
> concrete measure of how much of the domain RAMA can actually reach today,
> produced by introspecting the live models and the 88 registered tools. It
> quantifies the "enumerated, not generative" problem so the architecture
> decision rests on numbers, not vibes.

_Generated by inspecting `rama/registry.py` (tool surface) against each model's
fields via Django's `_meta`._

## Headline numbers

- **88 registered tools.** Each new capability costs ~5 files (wrapper + impl +
  `tool_meta` risk + persona lines + tests) plus a deploy.
- Across the core write-bearing entities, RAMA can set roughly **40–65% of the
  fields a landlord can legitimately edit** — and **~0%** of condition-inspection
  fields.
- **Reads:** almost every entity has a read tool, so entities are _readable_ —
  but only through **pre-shaped summaries**. There is **no composable query**: if
  a landlord asks something the read tool didn't pre-compute, the answer isn't
  reachable.
- Every historical gap (bills, shared areas, co-host, links, inventory, parking,
  per-date hours) is explained by this table — they were all editable
  fields/relations with no tool.

## Write coverage by entity

"Editable (landlord)" excludes system fields, derived/read-only fields, and
inbound data (e.g. an inquiry's name/email — the prospect owns those). "RAMA can
set" counts fields writable through some tool.

| Entity | Editable (landlord) | RAMA can set | Coverage | Notable unreachable writes |
|---|---:|---:|---:|---|
| **Property** | ~23 | ~10 | ~43% | `building_amenities`, `default_bills_included`, `neighbourhood`, `available_from`, beds/baths/size, lat/long, default deposit |
| **Lease** | ~30 | ~12 | ~40% | **`bills_included` on an existing lease**, `parking_*`, `occupants`, `rent_due_day`, `pets_terms`/`smoking_terms`, the 5 `landlord_service_*` contact fields, `custom_tenant_notice_months`, `fixed_term_end_*`, `move_in/out_date`, deposit-received dates |
| **LeaseTenant** | ~10 | ~4 | ~40% | `tenant_notes`, per-tenant `cleaning_fee`, `individual_start/end_date`, `is_primary_tenant` |

## A live example of the treadmill (found _during_ this audit)

`update_lease`'s parameters are: `total_rent, security_deposit, start_date,
end_date, pets_allowed, smoking_allowed, special_terms, house_rules,
shared_with, etransfer_email, is_month_to_month`.

It has **no `bills_included`.** We just shipped a Bills editor in the web UI and
a property-level default — but **RAMA still cannot set bills on an existing
lease**, because nobody added that one parameter to this one tool. This is the
treadmill in miniature: the data model, the serializer, and the UI all support
it; RAMA is blind to it until a human edits a wrapper. Under the proposed
architecture, `bills_included` would be one manifest entry marked
"editable while lease not locked," and RAMA could set it the day the field
existed — no tool change.

## Reads: entity-level yes, query-level no

Readable entities (via a `list_*`/read tool): properties, leases, lease roster,
tenants, appointments, viewing requests, work orders, inquiries, conversations,
messages, inspections, move events, inventory, expenses, ledger/charges,
deposits, bank balances, holdings, vendors, documents, the constitution,
notification channels, co-landlords, capability gaps.

But these return **fixed shapes**. There is no way for RAMA to answer a composed
question the read tools didn't anticipate — e.g. _"which active leases include
parking, rent over $800, and have no completed move-in inspection?"_ Every such
question is a latent read-gap, the mirror image of the write-gaps above.

## Links / artifacts

- **Present (new):** `open_lease`, `open_property`, `lease_pdf_info`.
- **Missing:** a property's photo set, tenant/lease documents, inspection
  reports, work-order photos — no link/artifact resolver. This is the class the
  "send me the PDF / the photos / the metadata" gaps came from.

## What this establishes for the architecture decision

1. The gaps are **not random** — they are the **unexposed majority** of a domain
   whose exposed minority was hand-curated. ~40–65% field write-coverage means
   the _default_ experience for any new ask is "not covered yet."
2. The fix is not "add the missing 60%" one tool at a time (that just moves the
   treadmill). It's to make the surface **derive from the domain** so coverage is
   ~100% by construction — the Domain Capability Manifest + generic
   `read`/`update`/`link` primitives in `RAMA_SMARTNESS_ARCHITECTURE.md` §4.
3. Highest-leverage, lowest-risk first move (Phase 1–2 there): generic **reads +
   links** over the manifest — they can't corrupt anything and immediately erase
   the read-gaps and the link/artifact gaps.

## Method / reproduce

```bash
docker compose -f docker-compose.local.yml exec django /entrypoint \
  python manage.py shell -c "from rentium.rama import registry as r; print(len(r.TOOL_FUNCTIONS))"
```
Field inventories came from each model's `_meta.get_fields()`; write coverage
from the `inspect.signature()` of the `update_*`/`create_*` tool wrappers in
`rama/tools.py`. Percentages are deliberately approximate (±a few fields on the
"landlord-editable" judgement call) — the point is the _order of magnitude_, and
the direction is unambiguous.
